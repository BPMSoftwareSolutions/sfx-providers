CAPABILITY BOUNDARY
    │
    ├── GIVEN / INPUT
    │
    ├── WHEN / EVENT
    │      └── execution cells
    │
    └── THEN / OUTCOME

And the external provider bindings are outside the capability boundary, which is directionally right.

The agent also stopped scattering quite as much unrelated stuff around the canvas. The main circuit now has an obvious center of gravity.

## The remaining problem

The `WHEN / EVENT` region is carrying **35 operations and 39 bindings simultaneously**.

That is too much for the default blueprint.

You're looking at something closer to:

```text
EVENT
  ↓
all execution responsibilities
  ↓
all mechanics
  ↓
all provider bindings
```

flattened into one plane.

That is why the center already looks dense despite the capability itself being conceptually simple.

### The default capability blueprint should probably collapse this

Something like:

```text
GIVEN
Public Equity Request
      │
      ▼
WHEN
Resolve Equity Market Price Evidence
      │
      ├── Resolve provider authority
      ├── Prepare governed request
      ├── Execute market-data exchange
      ├── Interpret provider response
      └── Admit attributable evidence
      │
      ▼
THEN
Equity Market Price Evidence
```

And then **click `Execute market-data exchange`** to get the current 35-operation view.

That is observation altitude working exactly as intended.

## The violet boxes are still visually overpowering

Every operation appears to have a violet binding label sitting directly over it:

```text
transformation
credential
http exchange
...
```

Those bindings are useful, but at this altitude they should probably be an **overlay**.

Default:

```text
┌──────────────────┐
│ build request    │
└──────────────────┘
```

Provider-binding overlay enabled:

```text
        [transformation]
               │
┌──────────────▼───┐
│ build request    │
└──────────────────┘
```

That would eliminate a huge amount of noise.

Same principle as telemetry:

> topology first; properties second.

# The outcome side needs stronger semantic geometry

The right side is interesting because I can see multiple result/disposition states:

```text
EQUITY MARKET PRICE ...
EQUITY MARKET PRICE ... [red]
NATIVE MARKET PRICE TESTIMONY
REJECTED
```

This should not look like a stack of status labels.

It should look like **declared outcome variants**:

```text
                     ┌─► PRICE_EVIDENCE_RESOLVED
                     │
classify outcome ────┼─► PRICE_EVIDENCE_REJECTED
                     │
                     └─► NATIVE_TESTIMONY_REJECTED
```

That's much more semantically meaningful.

The user should immediately understand:

> “Ah. These are possible terminal dispositions of this circuit.”

Not:

> “These are some boxes on the right.”

# I would tell the agent this

> **Keep this projection. It is useful as the Event / Execution observation altitude. Do not use it as the default capability blueprint. The default capability blueprint should collapse the 35 operations into a small number of semantic responsibilities. Bindings, mechanics, diagnostics, telemetry, and evidence are overlays or lower-altitude projections. Outcome variants should render as explicit terminal branches. Every provider must visibly connect through its owning port. Every retained declaration must either participate in the active route or move to inventory.**

And one more hard rule:

> **Increasing detail must happen by descending observation altitude, never by continually adding more objects to the same projection.**

That one rule will keep this whole visualization system sane as capabilities become much larger.
